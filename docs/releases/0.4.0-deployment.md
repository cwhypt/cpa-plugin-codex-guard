## Deployment incident: config inode watch

The first version of `scripts/deploy-shared-plugin.py` atomically replaced `config.yaml`. CPA's watcher observes the file inode rather than its parent directory. Replacing the inode removed that file watch, so the initial write did **not** activate the new version. Runtime remained healthy on `0.3.8`; this was detected by timeout, management version inspection and `/proc/<pid>/maps`.

The script is corrected to write validated config bytes **in place**, retaining the inode (artifact/backup writes remain atomic). The user explicitly selected **hot load only, no restart**. The existing authenticated management plugin-config PUT endpoint applied exactly the already prepared Guard config; semantic comparison showed no unrelated config values changed. That invoked the normal config reload callback and successfully loaded `0.4.0`.

**Outstanding operational limitation:** the config file's automatic filesystem watch remains absent in this running process. Reading/writing the new inode does not restore it. Apply subsequent config changes through authenticated management APIs, not file edits alone, until a separately authorized maintenance restart recreates the watcher. Do not claim the release restored automatic file watching. Auth-directory watching remains present. No host code, protected remote-connection services, database, or auth file was changed.

## Rollback without restarting

Use authenticated plugin-config PUT to restore **only** the previous Guard config stored in `guard.before.yaml` in the private backup. It selects store version `0.3.8` and removes session routing.
