# Codex Guard 0.4.0

## Included changes

- Configurable session-first routing, caller isolation and persistent one-hour sliding bindings.
- Local arithmetic/probe-cache hits precede classification and account selection.
- Confirmed SVG/candy tasks prefer the designated benchmark OAuth; ordinary requests retain the existing API-key preference; confirmed probes use the eligible priority-bounded weighted pool.
- Astra/sol requests with explicit medium-or-higher effort and sufficient user/context length can establish a quality-account binding. Short follow-ups retain that binding.
- Reserved account admission is checked during fallback as well as preferred selection.
- Atomic category resolution, canonical session IDs, persistent smooth weighted allocation and safe stream accumulation boundaries.

Source behavior and policy: `../session-content-routing.md` and `../quality-account-routing-2026-11-20.md`.

## Release procedure

Build a committed source snapshot into a temporary directory using:

```sh
CGO_ENABLED=1 GOOS=linux GOARCH=arm64 go build -buildvcs=false \
  -tags cshared -buildmode=c-shared -o <temporary>/cpa-codex-guard-v0.4.0.so \
  ./cmd/cpa-codex-guard
```

Run tests on that same snapshot, verify ELF/aarch64/shared-object type, the `cliproxy_plugin_init` export and artifact SHA-256, then exercise registration/routing/cache behavior through the compiled C ABI with temporary state files. Install a versioned artifact and update only Guard's store version and session-routing config, preserving the old artifact for rollback. Confirm the hot-reload log and process mapping without restarting CPA.

The release snapshot excludes the pre-existing unstaged README and Responses-replay edits. Deployment-specific identities, exact policy and verification evidence are recorded in the local deployment record; production secrets/config backups are not committed.

## Rollback

Restore Guard's previous plugin config (store version `0.3.8`, no session routing), preserving unrelated current config, so the retained `cpa-codex-guard-v0.3.8.so` can hot-load. Leave the new routing state file intact for investigation or future re-enablement. Do not restore a full old config over unrelated concurrent changes.
